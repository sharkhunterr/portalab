# Research — Community (spec 012, roadmap steps 22 · 23 · 24 · 25)

| # | Decision | Rationale | Alternatives rejected |
|---|---|---|---|
| R1 | **Community is a composition layer**: it owns the community surfaces, the activity feed projection, proposals, votes and participation — and **no engines**. Progression, achievements, quests, leaderboards and the ledger come from 013; funding lifecycle and reserved funds from 015 (CD-008); identity data from 002; visibility from 021 | Ownership (CD-008/CD-004), principle XX | Re-implementing rankings/rewards/funding |
| R2 | **Explicit non-goals enforced by tests**: no friends/followers/graph/DM/likes/reactions/native chat — the schema has no such tables, and a route-table test fails if any route/OpenAPI path matches forbidden patterns (`/friends`, `/followers`, `/messages`, `/dm`, `/like(s)`, `/reactions`, `/chat`); chat is a possible **plugin** (a `community.slot` extension point exists, no chat code) | FR-003/004 | Relying on review discipline |
| R3 | **Profiles are assembled per viewer**: sections (`identity`, `progression`, `achievements`, `activity`, `projects`, plus plugin-registered sections) are fetched independently, each passed through the 021 `VisibilityFilter` using the owner's preference and the viewer's relationship (`Public | Community | Leaderboards only | Private`); permission alone never exposes Private data | FR-001/002 | One monolithic profile query |
| R4 | **Members directory** lists accounts that are Active and whose "member listing" visibility ≥ Community for the viewer; implemented over `identity.directory` + visibility, with the same provider reused for global search | FR-001/025 | Own member table |
| R5 | **Activity feed = derived projection** of an allow-listed set of domain events (default `achievement.unlocked`, `user.level_up`, `quest.completed`, `project.created`, `project.status_changed`, optionally `media.finished` only when the actor's datum visibility allows) into `community.feed_entries` (idempotent on `source_event_id`); visibility is checked **at read time** (preferences can change) and again at write (Private actors never enter); entries carry only keys/params + source ref, localized by 026 at render; retention 180 days; no likes/reactions/comments | FR-005/006, CD-016 | Live join over the event store; storing localized text |
| R6 | **Leaderboards and quests/challenges are presentation only**: Community pages call 013's `LeaderboardService`/catalogs and render them with visibility/opt-out semantics defined there; hidden achievements stay hidden until unlocked; "challenge" = time-boxed quest (013 OQ-62 default) | FR-007..011 | Community-computed ranks |
| R7 | **Proposals (Idea stage, CD-008)**: `community.proposals` owns proposal content (Markdown via the 011 renderer), proposer, tags, optional moderation (`community.proposals.moderation`, default off — OQ-59 default: any active account may propose); creating a proposal registers a lifecycle record in Marketplace through the `ProjectLifecycle` port; project **state** is read from 015, never stored here | FR-012, CD-008 | Community-owned lifecycle |
| R8 | **Voting (OQ-58 default)**: one **up-vote of support** per active account per proposal, free, no minimum level (CD-007); a user may **retract and re-cast** while the lifecycle state accepts votes; eligibility is the **invariant "Active account"** (002 `is_active_account`), not a configurable permission, so Admin config cannot disable the locked rule; voter identities private by default — counts public, own vote visible to the voter, staff see aggregates | FR-013..016 | Ranked/multi-option votes; permission-gated voting |
| R9 | **Funding is not here**: Community UI links to 015's funding action; `project.funding_added` and reserved-funds rules belong to 015 via `EconomyService`; voting and funding stay independent (no coupling in data or UI logic) | FR-015..018, CD-008 | Funding endpoints in Community |
| R10 | **Participation & help (OQ default)**: members may *participate* in a project (`contributor|tester|helper`); a proposer/moderator may **recognize** a participation once, emitting `community.contribution_recognized`, which a 013 reward rule turns into Contribution (anti-abuse in 013 + Community-side limits: no self-recognition, ≤ N recognitions given per recognizer per day, ≤ 1 per recognizer→recipient pair per month). Staff manual Contribution grants go through 013 (marked, audited). "Help prompts" = a `help_wanted` flag + description on proposals surfaced in discovery — **no DM/chat/Q&A forum** | FR-022..024, FR-023 | Building a forum; peer "thanks" counters |
| R11 | **Discovery**: shelves (new members within visibility, projects needing votes/help, recent achievement unlocks, activity highlights) plus `SearchProvider`s for members and proposals (008 SDK); every empty state offers a next action | FR-025, FR-031 | Separate discovery index |
| R12 | **Degraded modes**: each section/source fails independently (gamification, economy, 015 unavailable ⇒ that block shows `unavailable`/`stale`, rest renders) | FR-031 | All-or-nothing pages |

No `NEEDS CLARIFICATION` remains; R7, R8, R10 are **plan defaults for OQ-55..59** (decision authority and reserved-funds rules are 015's).
