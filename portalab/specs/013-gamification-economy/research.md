# Research — Gamification & Economy (spec 013, roadmap steps 19 · 23 · 24)

| # | Decision | Rationale | Alternatives rejected |
|---|---|---|---|
| R1 | **One append-only `gamification.transactions` ledger for all three values** (`xp|contribution|coins`), enforced by DB triggers (no UPDATE/DELETE); corrections/refunds/destruction are new rows (`reverses_transaction_id`); `balances` is a transactional cache updated in the same transaction; balance non-negativity by `CHECK` + guarded `UPDATE … WHERE amount >= :x`; `portalab economy verify` recomputes balances from the ledger | FR-006/019..021/035; XP/Contribution need the same traceability for reconstruction | Separate ledgers per value; mutable balances only |
| R2 | **Reward rules are economy configuration, not a generic rule engine**: a closed record `{event_type, closed predicate over declared event attributes, grant formula (fixed | per_unit(field, factor, max)), static multiplier, limits}`; they can only produce ledger grants. Generic cross-domain WHEN/IF/THEN stays in Automations (019), which may call Gamification's bounded `grant_manual_reward` action. **Boundary flagged for confirmation** | CD-010 vs FR-004/025 (013 owns reward rules + versioning) | Implementing rewards as Automations (loses versioned economy semantics) ; a second generic engine |
| R3 | **Versioned rules by `effective_from` instant**: the version in force at the event's `occurred_at` decides the grant; every transaction stores `rule_key` + `rule_version`; a change publishes a new version (never edits); no retroactive re-granting in v1 (explicit, audited backfill would create *new* transactions) | FR-025/026/035, deterministic late events | In-place edits |
| R4 | **Idempotency** by `idempotency_key = (trigger_event_id, rule_key)` (or `(source_kind, source_ref, period_key)` for achievements/quests/manual), unique in the ledger; consumers use 007 `ctx.idempotent_effect` | FR-005, CD-012 | Timestamp-based dedup |
| R5 | **Level is derived** from total XP by a versioned curve (OQ-60 default: cumulative threshold `round(100 · n^1.5)`; curve table in config); `user.level_up` emitted only when an XP grant crosses a threshold; curve changes recompute the cached level silently | FR-002/003 | Storing level as a currency |
| R6 | **Modifier combination = multiplicative with configurable cap** (CD-024): `final = base · Π(rule multiplier, campaign modifiers)` with `Π ≤ economy.maxTotalBoost`; campaign modifiers come from 014 via the `ModifierProvider` port; **anti-abuse applies after multipliers on amounts (caps) and on occurrences (cooldown/diminishing) — multipliers never bypass it** | FR-011..013 | Additive; max-wins |
| R7 | **Anti-abuse guards** (deterministic, windowed counters keyed from `occurred_at`): cooldown (min seconds between grants per rule), per-period caps per rule and per value (amounts), diminishing returns (geometric or step curve on repeat count within a window). **Anomaly policy (OQ-61 default)**: threshold breach ⇒ **withhold + flag for admin review**; admin approve (creates the transaction) or reject; confirmed abuse reversed only by a **correction transaction**; optional explicit escalation of flagged anomalies to an Incident (016 `support.incidents.create`, setting `economy.anomaly.escalateToIncident`, default off) per the OQ-61 registry default | FR-014..018 | ML detection; silent drops |
| R8 | **Per-user serialization** of reward processing via advisory lock on user id; **late events** are evaluated against windows as of their own `occurred_at` and never retroactively invalidate later grants (documented); the ledger—not event replay—is the source for reconstruction, and a read-only `verify --replay` re-applies historical rule versions to events to detect drift | FR-035 determinism | Global ordering requirement |
| R9 | **Spending API for other modules**: `EconomyService.spend/refund` (service layer, not an HTTP permission) used by Marketplace (015) and Community funding (CD-008); user-initiated purchases go through the owner's API. Funding pools are tracked by 015; here a funding contribution is a `spend` with `source_kind=community_funding`, a failed project is refunds (new transactions) | FR-023, CD-008 | Escrow accounts in 013 |
| R10 | **No inter-conversion** among XP/Contribution/Coins (OQ-63 default: none); the model has no conversion operation | CD-004 | Optional conversion |
| R11 | **Achievements** (one-time, versioned definitions) with closed criteria `event_count(event_type, filter) ≥ N` (via `gamification.counters`), `statistic_at_least` (017 provider), `level_at_least`, `value_at_least`; unique `(user, achievement)`; rewards through the ledger. **Quests / daily objectives / challenges (OQ-62 default: a "challenge" is a time-boxed quest)** use period keys in the statistics time zone; completion once per period; reward auto-granted on completion | FR-007..010 | Per-feature ad-hoc badges |
| R12 | **Final deletion (FR-028/029)**: erasure participant writes `destruction` transactions for remaining Coins, removes balance/counter/progress rows, keeps ledger rows bound to the tombstoned `identity.users(id)` (anonymized by construction, no free text), excludes the user from leaderboards | CD-005, 002 deletion saga | Refunding or transferring Coins |
| R13 | **Leaderboards (slice B)**: computed from `balances` (all-time) and windowed `transactions` sums, materialized into `leaderboard_snapshots` by a job; metrics default `xp`, `level`, `contribution`, `achievements` (Coins excluded unless enabled); include only users whose visibility level (021 `progression` datum) allows leaderboards; viewer always sees own rank; ties by earliest attainment | FR-031, CD-016 | Live ranking queries over the ledger |
| R14 | **Simulation before publish**: `simulate` dry-runs a rule version against sample or historical events (no writes), showing grants, applied modifiers and guards | Admin safety (FR-027) | Blind publishing |

No `NEEDS CLARIFICATION` remains; R2, R5, R6, R7, R11 are **plan defaults for OQ-60..64**.
