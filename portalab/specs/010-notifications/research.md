# Research — Notifications & Communication (spec 010, roadmap step 15)

| # | Decision | Rationale | Alternatives rejected |
|---|---|---|---|
| R1 | **One producer API**: `notifications.send(CommunicationRequest)` is the only way to create a communication. System sources, modules, admin rules and (later) the Automations `communication.produce` action all call it. **010 contains no rule/trigger engine** | CD-010 (single WHEN→IF→THEN engine in 019), FR-012 | A notification rule builder in 010 |
| R2 | **Distinct concepts by data and API**: `kind ∈ {notification, alert}` in `notify.communications`; **News** stays in the News module (it may *call* `send` with a subject ref); **Email** is a channel (`channel=email`) with its own preference namespace and delivery rows. Alerts require `priority ≥ high`, have a separate UI treatment and policy | FR-001..004 | A single polymorphic "message" without kind |
| R3 | **Per-recipient rendering at delivery time**: message templates are ICU keys + params (026 catalogs, `RecipientLocale`); the rendered text is stored on the user's inbox row so history is immutable and language-correct | FR-028, i18n, history stability | Rendering at read time; storing sender-localized text |
| R4 | **Permission re-check at delivery**: each recipient is authorized against the communication's `subject_ref` right before fan-out/rendering; failure ⇒ `suppressed(permission_lost)` recorded, nothing delivered (FR-028/029). Audience resolution is a `AudienceSpec` (explicit users / permission / role / all authenticated) evaluated by 010 under the **caller's authority** (automation author cannot target an audience they cannot see) | CD-002/003 | Trusting the caller |
| R5 | **Preferences are user-tier settings in 020** (`notifications.preferences.<category>.<channel>`, `notifications.email.digest`), constrained by an admin **category registry** (`declare_category`: default channels, `mandatory_channels`, mutable flag); disabling one channel never affects another (FR-011); policy beats preference without deleting it (CD-011/016) | FR-008..011 | A separate preference store |
| R6 | **Baseline taxonomy (OQ-45 default)**: priorities `low|normal|high|critical`; categories declared by owner modules (`system.maintenance`, `system.health`, `account.security`, `support.*`, `media.*`, `community.*`, `gamification.*`, `marketplace.*`, `statistics.wrapped`, …); mandatory: `account.security` and `critical` alerts on the portal channel | Product input flagged | Hard-coded list |
| R7 | **Mute-bypass (OQ-49 default)**: critical Alerts bypass category/priority mutes and batching **on the portal channel only**; they never override email opt-out or the sound-off / reduced-motion accessibility preferences | Urgency vs consent/accessibility | Bypass everything |
| R8 | **Anti-flood (OQ-48 default)**: per-user/category coalescing window (`notifications.coalesceWindowSeconds`, default 120) merges repeats with the same `(category, subject)` into one item with a count; email via optional digest (`off|daily|weekly`); **critical alerts are never throttled or coalesced** | FR-032 | Hard drop |
| R9 | **System-generated maintenance reminders** (J-1, H-1, start, change/cancel) are a **fixed system source** inside 010 driven by 006 `maintenance.*` events and the jobs table (`run_at`), not a configurable rule; configurable variants move to 019 later. Late evaluation (OQ-46 default): fire once if still within `valid_until` (event start), else suppress `expired`; rescheduling/cancel (OQ-47 default): cancel pending reminders (dedup key includes schedule version) and send a corrective communication to those already notified | FR-020/021, CD-010 | Using the generic engine before it exists; configurable engine here |
| R10 | **Email = `EmailTransport` port + SMTP adapter** (`aiosmtplib`); credentials in `core.secrets`; delivery through outbox rows + `send_email` job with exponential backoff and attempt cap; plain-text + minimal sanitized HTML from catalog templates; no user-authored HTML; also implements 002's `VerificationChannel` | FR-026/027, self-hosted | Third-party mail API as hard dependency |
| R11 | **Realtime**: 004 SSE stream message `notification.created {id, kind, priority}` (no content); the client fetches the item via the authorized API; sound cue and toast are client-side from preferences and the 022 `SoundService`/`Notification` component; push is a future channel behind the same `Channel` interface | FR-022..025 | Embedding content in SSE |
| R12 | **Notification center API**: cursor-paginated inbox with unread/category filters, read/archive, unread count; items sorted by priority then time within the "important first" rule; retention per 021 (read items default 90 days) | FR-005/006/030 | Client-side sorting only |
| R13 | **Idempotency**: unique `(source, dedup_key)` on communications and `(communication_id, user_id, channel)` on deliveries | FR-014 | Best-effort dedup |

No `NEEDS CLARIFICATION` remains; R6–R9 are **plan defaults for OQ-45..49**.
