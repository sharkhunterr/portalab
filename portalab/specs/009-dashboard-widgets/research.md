# Research — Dashboard & Widget System (spec 009, roadmap step 12)

| # | Decision | Rationale | Alternatives rejected |
|---|---|---|---|
| R1 | **Widget = registered definition + a domain-owned data provider**: owners register `WidgetDefinition` (key, owner, permission, config schema, size limits, refresh hints, conditions, frontend component id) and a `WidgetDataProvider`. The dashboard module owns composition only | FR-030 (consume via domain contracts), ownership (no domain logic in 009) | Dashboard querying domain tables; hard-coded widget list |
| R2 | **Uniform data envelope** `WidgetPayload{state, as_of, stale_after_s, data, partial_reasons[]}` served by `GET /widgets/{key}/data`; the provider authorizes; the router enforces a per-widget timeout (default 5 s) and converts failures into `unavailable`/`error` states | Independent loading and per-widget functional states (FR-001/003/024) | Single aggregated dashboard payload (one slow widget blocks all) |
| R3 | **Frontend isolation**: each widget in its own `ErrorBoundary` + `Suspense` + own query; components lazy-loaded; a crashing widget renders the `error` state, siblings unaffected | FR-001/021 | Shared fetch for the page |
| R4 | **Layout model (OQ-41 default)**: 12-column grid, three breakpoints (lg ≥ 1024, md ≥ 640, sm < 640). Stored layout is an **ordered list with `{w,h}` per widget** (lg authoritative); md derived, sm is a single column in the same order. One saved layout per user (no multi-layout in v1). Keyboard-operable "move/resize" controls; drag is an enhancement, never the only way (WCAG 2.2 dragging movements) | FR-006/022/023, CD-027; DOM order = reading order | Free-form absolute positioning; per-breakpoint manual layouts |
| R5 | **Hide vs remove (OQ-40 default)**: *hide* keeps the instance and its config (`status=hidden`, re-addable in one click); *remove* deletes the instance and its config. Mandatory widgets can be neither hidden nor removed; locked widgets can be hidden/removed unless also mandatory but cannot be moved/resized/reconfigured | FR-005/010 | Treating both as the same |
| R6 | **Policy classes live in Administration config** (`dashboard.widgetPolicies` map validated against registered keys): `free|default|mandatory|locked|conditional|disabled` (+ optional `lockedConfig`). The **effective dashboard is computed on read** by overlaying policy onto the stored user rows, so a stricter policy never destroys the user's stored choices and relaxing it restores them (CD-016 preserve/restore) | CD-011 one config system, FR-013 | A `widget_policies` table; mutating user rows on policy change |
| R7 | **Conditional widgets (OQ-43 default catalog)**: `role_in`, `permission`, `service_state` (006), `campaign_active` (014), `module_enabled`, `data_present`. Evaluated server-side by a closed-set `ConditionEvaluator`; unknown condition ⇒ widget hidden + diagnostic | FR-011 | Free-form expressions (would become a second rules engine, CD-010) |
| R8 | **Refresh (OQ-44 default)**: per-widget `refresh` hint ∈ {`on_view`, `interval(s)`, `event(types)`}; client uses TanStack Query (`staleTime`, window-focus refetch); **event-driven invalidation** via the 004 SSE stream: the dashboard module maps registered `invalidate_on` event types to `widget.invalidate` messages (widget key only; the refetch re-authorizes). `stale` = `now − as_of > stale_after_s` | FR-031, no polling storms | Fixed polling for all |
| R9 | **Starter dashboard**: `dashboard.starterLayout` (ordered widget keys with sizes, optionally per role) applied once at the onboarding `dashboard` step (002 `OnboardingTracker`), filtered by permission/availability/policy; idempotent via `starter_applied_at` | FR-014/015 | Per-user manual setup |
| R10 | **Since Last Login** = aggregation of `ChangeSummaryProvider.changes_since(principal, since, limit)` registered by domains (permission/privacy applied at source, like search providers); ranking by type priority + recency, capped (default 20). `since = max(last_summary_seen_at, now − lookbackDays)`; boundary advances only when the user **acknowledges/dismisses** or after a configurable inactivity gap — robust for concurrent sessions (OQ-42 default, lookback 30 days) | FR-016..018 | Querying the central event store directly (privacy risk); `last_login` timestamp (breaks with concurrent sessions) |
| R11 | **Marketplace/plugin widgets are declarative** (data source via the owner's provider + one of the standard templates `stat|list|chart|timeline|status`) — **no arbitrary plugin JS in the dashboard**; richer sandboxed widgets are a 023 decision | FR-019..021, security | Executing plugin bundles in the SPA |
| R12 | **Presentation vs state**: widgets render states exclusively through the 022 `FunctionalState` component and theme tokens; no widget implements its own state colors | FR-026/027 | Per-widget styling of states |

No `NEEDS CLARIFICATION` remains; R4, R5, R7, R8, R10 are **plan defaults for OQ-40..44**.
