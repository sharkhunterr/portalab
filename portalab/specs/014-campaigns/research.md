# Research — Campaigns / Events (spec 014, roadmap step 20)

| # | Decision | Rationale | Alternatives rejected |
|---|---|---|---|
| R1 | **Campaign ≠ Domain Event** (CD-009): module `campaigns` owns the time-bound themed contextualization; its lifecycle emits Domain Events `campaign.*` | Terminology resolution | Reusing "event" for both |
| R2 | **Authoritative activity history = `campaigns.activation_log`** (append-only intervals with `tstzrange` and a GiST **exclusion constraint** per campaign preventing overlaps). Eligibility for any occurrence is `∃ interval ∋ occurred_at` (FR-020), so late/duplicate deliveries resolve identically; schedule jobs and manual overrides only open/close intervals | FR-020/023, determinism | Recomputing schedule on demand (breaks with manual overrides and edits) |
| R3 | **Schedule model (OQ-66 default)**: `none | yearly (month/day window) | custom (every N days/weeks/months from an anchor)`, evaluated as **wall-clock in the campaign's time zone** (default portal tz) through the 026 `resolve_wall_clock` policy (DST-safe); the next occurrences are materialized in `campaigns.occurrences`; boundary jobs (`run_at`) open/close intervals and emit `campaign.started|ended|ending_soon`; a per-minute reconciler repairs missed boundaries | FR-001..003 | Cron strings; relative-only durations |
| R4 | **Manual override precedence (OQ-69 default)**: manual *activate/deactivate* overrides the schedule **until the end of the current occurrence (activate) or until the next scheduled start (deactivate)**, or an explicit `until`; always recorded with actor/reason/confirmation; the schedule then resumes automatically. State model Draft → Scheduled → Active ⇄ Paused → Ended → Archived | FR-004 | Permanent overrides |
| R5 | **Conditions = closed catalog** (no expressions): `media_kind ∈ …`, `genre ∈ …` (tag-based on canonical normalized tags), `title_contains` (NFKC + casefold + diacritics-insensitive substring over original and effective titles — OQ-68 default), `activity ∈ event types`, `audience` (all | roles | groups | level range via `ProgressionReader` | user list). Modifier = `{value, factor, when: ConditionSet (AND)}` | FR-008..010, CD-010 | Free-form rule expressions |
| R6 | **Attributes via capabilities (FR-009)**: an `ActivityAttributeProvider` registry per event-type prefix returns `{media_kind, genres, title, …}` for the occurrence (media provider supplied by 024); unknown/unavailable ⇒ condition evaluates *unknown* ⇒ modifier **not applied** (no false grant, FR-025) and counted | Decoupling | Hard-coding media fields |
| R7 | **Supply modifiers, don't grant**: Campaigns implements 013's `ModifierProvider.modifiers_for(user, event, value, at)` returning one `Modifier{source_ref=campaign:key:version:modifier_id, factor}` per matched modifier (at most once per modifier per occurrence). **Combination arithmetic is Gamification's CD-024** (multiplicative, capped, one grant per occurrence/rule via idempotency) — Campaigns documents but does not re-implement it | FR-006/015..019, CD-024 | Campaigns computing final amounts |
| R8 | **Versioning**: every edit creates an append-only `campaigns.versions` row with `effective_from`; resolver picks the version in force at `occurred_at`; grants carry `campaign_key@version` in their modifier refs; ending/changing never rewrites history | FR-021..023 | In-place edits |
| R9 | **Campaign-scoped achievements/quests** live as nested definitions in the campaign version and are exposed to 013 through a `CampaignContentProvider` (active-at-instant lists); 013 evaluates and grants through its ledger (no parallel reward mechanism). Requires a `DefinitionSource` extension point in 013 (follow-up) | FR-011 | Duplicating definitions into 013 tables |
| R10 | **Theme contextualization**: the campaign names a theme from the 022 registry; `GET /campaigns/active/presentation` returns the per-user effective campaign theme (audience-filtered, priority-ordered); the SPA applies it as an overlay **only** if admin policy allows the theme and the user has not opted out (`ui.campaignThemes`, follow-up for 022); accessibility preferences always win (022 rule) | FR-012 | Campaign-specific styling code |
| R11 | **Communications (FR-013)**: Campaigns emits `campaign.started|ending_soon|ended`; **configurable** announcements are Automations (019) rules reacting to those events with the 010 action (CD-010) — the campaign console offers preset automation templates; before 019 exists, an Admin can send a manual announcement via 010 `notifications.broadcast` (manual action, audited), not a rule | CD-010 | A campaign-owned notification scheduler |
| R12 | **Calendar and reader ports**: implements `CalendarSource(kind=campaign)` (011) and `CampaignReader` (`is_active(key, at)`, `active_for_user(user, at)`) for 009 conditional widgets and 017 unlocks | Existing contracts | Duplicate schedule logic |
| R13 | **Simulation**: `POST /admin/campaigns/{id}/simulate` evaluates a sample occurrence through the real resolver (active intervals, audience, conditions) and reports resulting modifiers — no writes | Safe configuration | Blind publish |

No `NEEDS CLARIFICATION` remains; R3, R4, R5, R7 are **plan defaults for OQ-65..69** (combination = CD-024; cap value is Gamification config `economy.maxTotalBoost`).
