# Research: Visual Experience (027)

All decisions below resolve the Technical Context of `plan.md`; no `NEEDS CLARIFICATION` remains. They build
on what 004 (shell), 009 (dashboard), 013 (progression), 022 (themes) and 023 (plugins) already ship.

| # | Decision | Rationale | Alternatives rejected |
|---|----------|-----------|-----------------------|
| R1 | **Navigation sections = the existing navigation `group`, promoted to a registered `NavigationSection`** (`key`, `label_key`, `icon`, `order_hint`, `audience: everyone\|administration`, `owner`) in `capabilities.navigation` (`register_section`). Contributions keep their `group` field (now meaning *section key*) and gain an optional `topic` (admin sub-groups). Built-in sections: `home`, `media`, `content`, `services`, `support`, `community`, `marketplace`, `admin`; the personal group `me` is no longer rendered in the main navigation but in the personal menu. Unknown section ⇒ owner's default section (declared with the section) else fallback `more`; never dropped (FR-010) | Reuses 004 assembly, filtering, admin layout (`groups_of`, `group_order`), ETag/epochs and plugin withdrawal; a closed schema field with a default keeps `schema_version` 1 (additive) | A second "menu" registry (duplicate mechanism, XX); hard-coded frontend grouping (plugins could not join a section) |
| R2 | **Section rendering rules on the server**: the assembler returns `sections: [{key, label_key, icon, audience, topics?: [{key,label_key,entries}], entries}]`; empty sections are omitted; single-entry sections carry `direct: true`. Response keeps `groups` (deprecated alias) for one release so older clients keep working | Filtering stays server-side (no leaked names, VI); the client only renders | Client-side grouping of a flat list |
| R3 | **Default membership**: every built-in contribution (all declared in `modules/shell/builtin.py`) is re-assigned (e.g., `support.*` → `support`, `community.*`/`gamification.progression`/leaderboards/quests → `community`, `marketplace.*` → `marketplace`, `news/wiki/calendar` → `content`, `health.services`/`statistics.page` → `services`, `media.*` → `media`, all `*.admin`/moderation/audit/roles/config → `admin` with topics `access`, `services`, `content`, `economy`, `system`, `extensions`). Personal entries (`identity.account`, `ui.appearance`, `i18n.language`, `notifications.preferences`, `privacy.center`, `media.accounts`, `notifications.center`) move to section `me` | Meets SC-002 (≤ 9 sections; admin = 8 + `me` in the avatar menu) | Leaving the 22 admin links in the sidebar |
| R4 | **Navigation preferences** (expanded sections, welcome dismissed) are **user-tier settings** in Administration (`shell.navigation.expanded: list[str]`, `shell.welcome.dismissedAt`) — account-level, follow the user across devices (FR-015, FR-029), mirrored to localStorage for first paint like 022 | One configuration system (CD-011); no new table | A `shell.user_prefs` table |
| R5 | **Header = composition of existing endpoints**, each fetched independently (FR-005): `GET /me` (name, `has_avatar`), `GET /users/{id}/avatar`, `GET /me/progression` (level, `level_floor`, `next_level_at`, xp, coins), `GET /me/notifications/unread-count`. No aggregate endpoint: an outage of gamification must not fail the identity part | Partial failure stays partial (IX); zero new privacy surface (own data only, VII) | A `/me/header` aggregate (single point of failure, cross-module coupling in the API) |
| R6 | **Live header updates**: gamification publishes a user-audience live event `progression.changed` (`{xp, level, coins, reserved_coins, level_up: bool, delta_xp, delta_coins}`) through `core.live.publish_live` inside the ledger transaction that changes XP/Coins (same outbox → consistent, no ghost updates on rollback). The client patches the TanStack Query cache; `level_up` triggers the celebration once (dedup by event `seq`). Notifications already publish unread changes | Reuses the 004/010 SSE stream (no polling); audience filter guarantees own-data only | Polling `/me/progression` every few seconds |
| R7 | **Layout profiles are a closed vocabulary** added to the theme document (schema **v2**): `layout: { nav: { desktop: "sidebar"\|"topbar"\|"rail", tablet: "rail"\|"topbar"\|"drawer", phone: "bottom-bar"\|"drawer" }, header: "full"\|"compact"\|"centered", cards: "elevated"\|"flat"\|"outlined"\|"glass", content: "narrow"\|"wide"\|"full", corners: "square"\|"soft"\|"round", widgetFrame: "card"\|"plain"\|"glass" }`; `motion: { profile: "none"\|"subtle"\|"lively"\|"playful", celebration: "none"\|"sparkle"\|"confetti"\|"glow" }` (keeps `fastMs/normalMs`); `sounds` keys extended to `notification, alert, success, reward, levelUp, ui`. The shell maps each choice to a `data-*` attribute on `<html>` + CSS variables; components switch arrangement by attribute selectors and small React branches (nav placement) — never theme-provided CSS or code (FR-032) | Themes stay inert data (022 R2, OQ-108); every option is implemented and tested once by the portal, so a Marketplace theme cannot break layouts; v1 themes upgrade by defaulting the new blocks | Free-form theme CSS/HTML (security, untestable); per-theme React components (code in themes) |
| R8 | **Theme families for light/dark variants**: theme v2 adds optional `family` (e.g., `portalab`) and the user preference `ui.colorMode: "dark"\|"light"\|"system"` (default `dark`). Selecting a family resolves to the member whose `colorScheme` matches the mode (system ⇒ `prefers-color-scheme`). Built-ins: `portalab-dark` (default) and `portalab-light` (family `portalab`), existing `light`, `dark`, `high-contrast` kept. A stored `ui.theme` that no longer exists falls back to the default (022 OQ-107) | Satisfies clarification Q3 (dark by default, light variant, optional follow-device) without duplicating the preference model | One document holding two palettes (doubles floor checks per document, breaks 022 floor report) |
| R9 | **Glass/blur degradation (FR-030a)**: `cards: "glass"` renders `backdrop-filter` only when `@supports (backdrop-filter: blur())`, not `prefers-reduced-transparency`, not `ui.contrast=high`; the floor check evaluates glass surfaces with their **solid fallback color** (declared in theme `colors.surfaceRaised`) so contrast is guaranteed whatever the device | Contrast floor stays computable and deterministic | Measuring blended colors at runtime |
| R10 | **Dashboard 2D model**: `widget_instances` gains `x` (column 0–11) and `y` (row ≥ 0); `w/h` kept, `position` kept as **derived reading order** (sorted by `(y, x)`) for tablet/phone and screen readers. Engine (`frontend/src/features/dashboard/grid/engine.ts`, pure TS, mirrored server-side validation in `modules/dashboard/arrangement.py`): collision resolution pushes overlapped widgets down, then **vertical compaction** (each widget moves up while free). Server validates bounds (`0 ≤ x`, `x + w ≤ 12`, size limits per widget, no overlap) and stores the compacted result; If-Match versioning unchanged | Deterministic, unit-testable both sides; DOM order = reading order keeps WCAG 1.3.2 | `react-grid-layout` (absolute positioning, DOM order ≠ visual order, width measuring, React 19 support lagging); free-form pixel layout |
| R11 | **Derived tablet/phone views**: tablet (6 columns) = widgets in reading order, `w' = min(w, 6)` rounded to 3 or 6, re-flowed with the same engine; phone = single column (or 2 for `w ≤ 3` small stat widgets), reading order. Never stored (FR-045) | Same engine, no extra state | Stored per-device layouts (rejected by Q2) |
| R12 | **Drag & resize without a library**: Pointer Events (mouse/touch/pen) with pointer capture, grid snapping, a placeholder ghost, live preview through the engine, auto-scroll near edges; `touch-action: none` only on handles. Keyboard: select a widget (Enter), arrows move by one cell, Shift+arrows resize, Escape cancels, announcements via the 022 `useAnnounce`. Buttons (move/resize/hide/remove) stay available (WCAG 2.5.7) | No dependency, full control of a11y and touch | `dnd-kit` (lists/sortable focus, not 2D grids with resize); HTML5 DnD (no touch) |
| R13 | **Edit session**: entering edit mode snapshots the arrangement; changes apply locally (optimistic) and are saved with one `PUT /dashboard/arrangement` on "Save" (If-Match); "Cancel" restores the snapshot (FR-042). Gallery = `GET /dashboard/catalog` (already has title/description/icon/min/max) + a static preview per template (`stat/list/chart/timeline/status`) or the widget's own preview component | One write per session (no write storm while dragging) | Saving each drag step |
| R14 | **Migration of existing dashboards** (FR-044): Alembic `dashboard_0002` adds `x`,`y` (nullable), back-fills by flowing instances in `position` order into a 12-column grid with the engine's algorithm (Python port), then sets NOT NULL + check `x + w <= 12`; starter layouts (`dashboard.starterLayout`) accept optional `x,y` (flowed when absent) | No lost widget/config (SC-012); deterministic | Resetting dashboards to the starter |
| R15 | **Icons**: `lucide-react` (ISC, tree-shaken per icon) behind a design-system `Icon` component keyed by stable names (`icon` fields in navigation/widgets/themes reference names, not components); unknown name ⇒ neutral dot | Labels + icons are required (principles); named mapping keeps declarations data-only | Hand-drawn SVG set (maintenance); icon fonts (a11y issues) |
| R16 | **Typography**: self-hosted variable fonts via `@fontsource-variable/inter` (UI) and `@fontsource-variable/plus-jakarta-sans` (display/headings), bundled by Vite (no external requests — the portal is self-hosted and CSP forbids third-party fonts) | Modern, legible, OFL-licensed, offline | Google Fonts CDN (privacy/CSP) |
| R17 | **Motion & celebrations**: CSS transitions/keyframes driven by `--motion-*` variables per profile; page transitions via the View Transitions API when supported (progressive); celebrations (sparkle/confetti/glow) as a lightweight canvas/CSS component in `design-system/feedback/Celebration.tsx`, coalesced (one at a time, queue max 1) and disabled by reduced motion; number changes (XP/Coins) animate with a counter that respects reduced motion | No animation library (XX); reduced motion global switch already exists (022) | `framer-motion` (≈40 kB, overlapping with CSS variables approach) |
| R18 | **Sound sets**: default sets are short synthesized tones generated once by `frontend/scripts/gen-sounds.mjs` (WAV → committed `.ogg`/`.wav` under `frontend/public/assets/sounds/<set>/`), referenced as `asset:<set>/<name>.wav`; `SoundService` gains events `reward`, `levelUp`, `ui`; sounds stay off by default (022) | No licensing risk, tiny files, bundled assets only | Third-party sound packs |
| R19 | **Responsive classes**: phone `< 640px`, tablet `640–1023px`, desktop `≥ 1024px` (`useBreakpoint` already exists, aligned with 009 R4 `sm/md/lg`); shell arrangement chosen from `layout.nav[class]`; switching class keeps React state because the outlet subtree is not remounted (nav component swaps beside it) | Same breakpoints as dashboard grid; state preserved (FR-021) | Separate mobile routes |
| R20 | **Page composition kit** in `design-system/components/`: `PageHeader` (title, context, primary/secondary actions, breadcrumbs slot), `Card` (variants from `layout.cards`), `Tile`/`TileGrid` (artwork-forward media/product/project tiles with image fallback), `ListItem` (leading avatar/icon, meta, trailing action), `StatFigure`, `ProgressBar` (XP style), `Skeleton` (text/tile/list/card shapes), `EmptyState` (icon/illustration, message, next action), `Avatar` (image → initials with stable hue from user id), `CoinBadge`, `LevelBadge`. Every feature page migrates to them (SC-007); a lint check (`scripts/check-page-header.mjs`) asserts each route page renders `PageHeader` | One kit for modules and plugins (X, FR-037); measurable SC-007 | Restyling each page ad hoc |
| R21 | **Plugin & Marketplace themes v2**: same validation path (`POST /admin/ui/themes`, floor report) — the backend mirror (`modules/ui/themes/definition.py` + `theme.schema.json`) is regenerated from the frontend zod schema (existing `UPDATE_THEME_SCHEMA` flow); v1 documents are upgraded on read (`schemaVersion: 1` ⇒ defaults for `layout/motion.profile/family`) | One theme pipeline (022/023) | A separate "layout pack" product type |
| R22 | **Welcome & sign-in**: sign-in/registration/recovery/first-run reuse an `AuthLayout` (centered card over the theme background/artwork); the first-visit welcome is a dismissible `WelcomeCard` on the dashboard (not a modal tour) driven by `shell.welcome.dismissedAt` | Simple, non-blocking, keyboard friendly | Multi-step modal tours |
| R23 | **Testing**: unit (engine collision/compaction/derivation, section assembly, theme v2 parsing/upgrade/floor, header degradation, celebration coalescing), backend integration (sections assembly/filtering/fallback, arrangement validation + migration back-fill, `progression.changed` live event audience), Playwright (header on 3 widths, nav sections, phone bottom bar, drag/resize + keyboard path, theme switch with different layout profiles keeps state, 320 px reflow, axe per built-in theme × 3 widths) | Maps SC-001…SC-012 to automated checks; SC-005/SC-011 hallway tests documented in quickstart as manual | — |
