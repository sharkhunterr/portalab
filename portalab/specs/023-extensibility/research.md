# Research — Extensibility: plugins, discovery, feature lifecycle (spec 023, roadmap step 27)

This plan closes the decision deferred by spec 001 ("plugin packaging/isolation → 023").

| # | Decision | Rationale | Alternatives rejected |
|---|---|---|---|
| R1 | **Tiered plugin model.** *Tier 1 — declarative plugins*: manifest + data only (widgets via templates, themes, statistic packs, locale catalogs, automation templates, wiki content, nav entries, page definitions, product types) — **no code executed**. *Tier 2 — trusted code plugins*: Python packages installed by the **Admin only**, loaded in-process (app + worker) behind guarded hooks. *Tier 3 — out-of-process / sandboxed UI plugins*: reserved for untrusted third parties (future, same manifest + extension API over HTTP) | Honest security story for a single-Admin self-hosted portal; Tier 1 covers most Marketplace needs safely | Pretending in-process Python is a sandbox; mandatory out-of-process (operationally heavy) |
| R2 | **Trust model (OQ-111 default)**: only the single Admin installs or enables plugins; Marketplace "plugin" products reference a package the Admin already installed/approved (015 R10). Installation shows a **review screen** (permissions, extension points, event types, personal-data flags, capabilities, schema, checksum); package integrity = recorded SHA-256 (+ optional detached signature check, future) | CD-001, FR-027 | Auto-install from users or the internet |
| R3 | **Isolation guarantees (OQ-110 default)**: *data* — each plugin owns schema `plugin_<key>` and a dedicated PostgreSQL role (`plugin_<key>`) with grants only on its schema and `statement_timeout`; plugin code gets a `PluginDb` that does `SET LOCAL ROLE`, so it **cannot read core tables** (core data only via capabilities); *failure* — every hook (route, event handler, action, widget provider, nav/page contribution) runs inside `PluginGuard` (try/except, timeout, error counters, auto-**quarantine** after N errors/10 min, Observability report); plugin event/job handlers run in the **worker** process, never in the web process; *resources* — per-plugin rate/payload/concurrency limits. **Documented limit:** in-process code cannot be preempted or memory-capped; hard isolation is Tier 3 | Realistic guarantees, no false claims | Claiming sandboxing; per-plugin containers in v1 |
| R4 | **Packaging**: a Python wheel (or extracted directory) containing `plugin.toml` (manifest) and code under a distribution entry point `portalab.plugins`; Admin uploads (or drops into `plugins/available/`) → validated → extracted into `plugins/installed/<key>/<version>` and added to the plugin loader path (**no pip into the core environment**); static assets served from `/plugins/<key>/assets/` with image-only CSP | Isolated versions on disk, easy rollback | `pip install` into the app venv |
| R5 | **Manifest** (schema-validated): `key`, `name`, `version` (semver), `scope` (`portal|user`), `maturity` (`experimental|beta|stable|deprecated`), `requires_portal` range, `requires_capabilities[{name, range}]`, `requires_plugins[{key, range}]`, `provides{capabilities, events, permissions, settings, extension points}`, `personal_data` flag (+ classification), `migrations` branch, `i18n`, `ui` (declarative contributions), `entry_point` (Tier 2) | FR-002/017/018/020 | Free-form metadata |
| R6 | **Lifecycle states**: `installed → (needs_configuration) → enabled ⇄ disabled → archived`, plus `update_pending`, `update_failed`, `incompatible`, `quarantined`. **Enable/disable are live** (registrations added/removed dynamically); **first load of new code or an update needs a graceful process restart** (`needs_restart` flag; Python cannot reliably unload/reload modules) | FR-001/002, honesty about Python | Hot reload promises |
| R7 | **Clean removal by construction**: plugins register only through `PluginContext`, which records every contribution in a **contribution ledger**; disable/quarantine unregisters all of them from every registry (nav 004, widgets 009, search 008, calendar 011, statistics 017, automations 019, AI tools 018, categories 010, themes 022, i18n 026, permissions 003, settings 020, events 007, product types 015, media types 024, profile sections 012, connectors 005). A **conformance sweep** test proves every registry is empty for that owner after disable | FR-006, no broken slots | Each registry implementing removal ad hoc |
| R8 | **Data retention**: disable/archive never delete data; **purge** is a separate permissioned (`plugins.purge`), confirmed, audited action that optionally exports first and then drops the plugin schema/role; plugin-created data references core objects by opaque id (no FK) and the core never depends on it (OQ-114 default) | FR-005/007/023 | Delete on uninstall |
| R9 | **Dependencies & compatibility (FR-002/020)**: a resolver builds the graph from manifests, detects cycles/missing/incompatible ranges, orders loading topologically, blocks disabling a plugin with enabled dependents (or offers a confirmed cascade); capability requirement ranges are checked against the 001 registry; portal version range against the running version | FR-020 | Best-effort loading |
| R10 | **Updates & rollback (OQ-112 default)**: stage new version beside the current one → compatibility check → run **expand-only** migrations in a transaction → mark `update_pending` → restart → **probation window** (default 10 min) with health check; failure ⇒ automatic switch back to the previous package; destructive ("contract") migration steps are allowed only in a later version after a configured delay | FR-021/022/028 | In-place overwrite |
| R11 | **Extension-point catalog (OQ-113 default)**: only the **official** points that other specs already expose (listed in the plan); plugins can *expose events/capabilities* for other plugins but **cannot define new extension points** in v1. Conflicts resolve by `(priority config, plugin key, contribution id)`; singular points are first-wins with the loser flagged in diagnostics | FR-011..015 | Plugin-defined points |
| R12 | **UI extensions are declarative** (page definitions built from design-system blocks: markdown (011 sanitizer), stat/list/table/chart bound to plugin data endpoints returning typed states, forms from JSON Schema → plugin actions) — **no plugin JavaScript executed in the SPA** in v1; richer UI = future Tier 3 sandboxed iframe | FR-019, 009 R11 | Plugin bundles in the SPA |
| R13 | **Permissions**: plugin permissions are namespaced `plugin:<key>.<name>`, declared in the manifest, approved at install, **never reserved/Admin-only keys**; per-user plugins (`scope=user`) gate every contribution with `plugin:<key>.use`, granted by Marketplace acquisition through 003 — so the same permission filtering applies everywhere | FR-017/019/025 | A second visibility mechanism |
| R14 | **Plugin events**: namespaced `plugin.<key>.<type>`, schemas registered with 007 (validated/quarantined there, FR-029); plugin consumers idempotent via 007; plugin AI tools default to non-sensitive classes and the Admin may only *raise* sensitivity | FR-016 | Free-form events |
| R15 | **Discovery & feature lifecycle**: discovery = scan of `plugins/available/`, Marketplace plugin products, and (future) a configured remote index — never automatic internet access; **maturity** (`experimental → beta → stable → deprecated`) is shown in admin with deprecation notices; **module toggles** (first-party modules) use 020 `ToggleService` with this plan's dependency resolver and the same contribution-ledger removal | Roadmap step "Plugins / Discovery / Feature Lifecycle", FR-004 | Remote auto-update |
| R16 | **Reference assets**: a published `portalab.sdk` surface (capabilities + registries + `PluginContext`), a sample plugin (declarative + code), CLI `portalab plugin validate|pack|install|enable|disable|purge`, and CI contract tests so plugin authors can verify compatibility | Operability | Undocumented internals |

No `NEEDS CLARIFICATION` remains; R2, R3, R6, R10, R11 are **plan defaults for OQ-110..114**.
